# 《变形钢姬》MVU 设计与静静施工边界 v1.0

状态：设计冻结候选

## 0. 设计目标

本卡 MVU 保持极简，只承担三件事：

1. 锁屏：汽车人与霸天虎两方标志各占半屏，作为唯一入口。
2. 第1页：汽车人 / 霸天虎两方对玩家的阵营好感度。
3. 第2页：成熟网易云播放器模块。

MVU 不负责时间线切卷，不负责世界书业务条目开关，不负责角色/地点/设定触发，不建立人物收藏册，不建立第三套人物好感。

## 1. 施工权限硬边界

静静只负责 MVU 独立模块、MVU 技术世界书片段、视觉素材与 MVU QA。

严禁修改或覆盖：

- `build/worldbook/变形钢姬_worldbook_v1.0.0.json`
- `worldbook/**`
- `timeline/**`
- 现有角色、能力、地点、蓝灯、绿灯正文
- `manifest/worldbook-assembly.v1.json`

若 MVU 需要咩咩全栈四条技术世界书条目，只允许单独输出到例如：

`mvu/technical-worldbook-fragment.json`

不得直接把技术条目写回正式业务世界书。最终整卡装配时由我们的装配流程追加。

## 2. 锁屏设计

### 2.1 构图

- 整体为深色机械金属面板。
- 左半屏：汽车人标志，尺寸尽量大，主色偏红 / 暖金属。
- 右半屏：霸天虎标志，尺寸尽量大，主色偏紫 / 冷金属。
- 两半之间使用一道窄的发光机械缝或火种能量裂隙分隔。
- 标志本身是锁屏视觉主体，不再叠加角色立绘、轮播图、复杂封面。
- 中央或下方保留一个明确的进入热区；Android 触控区域至少 44×44px。

### 2.2 行为

- 点击中央进入 MVU。
- MVU 内保留一个小型“返回锁屏”按钮。
- 锁屏无左右翻页、无随机图、无自动剧情功能。
- 重新锁屏不应停止网易云播放；仅聊天切换 / 模块销毁时清理播放器。

## 3. MVU 页面结构

MVU 解锁后只有两页：

### PAGE 1：阵营好感

只显示两个阵营：

- 汽车人
- 霸天虎

每一方显示：

- 阵营标志
- 当前好感数值 `-100 ～ 100`
- 当前阶段
- 本回合变化值
- 本回合原因
- 一条以 0 为中线的双向进度条

阶段沿用《三国无双姬》成熟分段：

- `-100 ～ -80`：不死不休
- `-79 ～ -50`：敌视
- `-49 ～ -20`：对立
- `-19 ～ -1`：警戒
- `0 ～ 19`：中立
- `20 ～ 39`：友善
- `40 ～ 59`：认可
- `60 ～ 79`：信赖
- `80 ～ 99`：同盟
- `100`：生死与共

UI 自己根据数值计算阶段，不相信模型额外写出的阶段文本，避免阶段与数值不一致。

### PAGE 2：网易云

直接复用已经成熟的网易云模块，不重新设计另一套播放器。

必须保留：

- 单 iframe / 单播放器实例。
- 支持歌曲 / 歌单 URL 或 ID 解析。
- 页面切换、返回锁屏、普通 DOM 刷新时不断播。
- 无效输入不得摧毁当前正常播放实例。
- 不保存账号、Cookie、密码或任何网易云凭据。
- Android / SillyTavern 触控优先。
- 若浏览器拦截自动播放，保持用户手动点击播放，不做强制绕过。

具体默认歌曲 / 歌单后续由用户决定，本设计稿不提前绑定。

## 4. 阵营好感的唯一真值源

本卡不为阵营好感建立 stat_data 数值，也不使用 JSONPatch 维护汽车人 / 霸天虎好感。

唯一真值源为聊天历史中最近一个合法、完整的：

```text
<causality>
汽车人好感: 0/100｜本回合: +0｜原因: 无
霸天虎好感: 0/100｜本回合: +0｜原因: 无
</causality>
```

注意：

- 数值合法范围：`-100 ～ 100`。
- 两行必须同时存在，顺序固定。
- `本回合` 必须为整数。
- `原因` 必须是单行简短事实，不允许嵌套 XML / HTML。
- 任意一行不合法，则整个块作废，继续向历史消息回退寻找上一个合法完整块。
- 不允许半块继承，不允许汽车人取这一楼、霸天虎取另一楼。

## 5. `<causality>` 正文输出保险

参考《无职转生·因果法典》的成熟保险方案，本卡必须在卡级指令中写死：

每次正常 assistant 回复结束前，必须额外输出且只输出一个完整 `<causality>...</causality>`。

硬规则：

1. 即使两方本回合都没有变化，也必须输出完整块。
2. 若历史存在合法块，必须继承上一合法块的最终值后再结算本回合。
3. 若历史不存在合法块，汽车人 / 霸天虎初始均为 0。
4. 不得把 `<causality>` 包进 `<status>`、`<affinity>`、`<special_status>`、`<memory_log>`、`<wlog>` 或其他标签内部。
5. 推荐作为回复最后一个结构化块。
6. 禁止输出第二个 `<causality>`。
7. `<causality>` 只负责两大阵营好感，不承担人物个人好感、信任、关系或世界变量。

建议卡级保险正文：

```text
【阵营好感输出保险】
每次正常assistant回复结束前，必须额外输出且只输出一个完整<causality>...</causality>。
该块独立于status/affinity/特殊状态/记忆/wlog等预设变量槽，即使本回合两方好感均无变化也不得省略。
禁止输出第二个causality块。
```

## 6. 好感结算规则

为了避免模型每句话都乱加分，阵营好感采用《三国无双姬》式离散变化，不允许自由生成任意大整数。

合法本回合变化值：

`0, +1, +3, +5, -1, -5, -10, -50`

建议语义：

- `0`：普通交流、阵营无关事件、只有个人私交意义。
- `+1`：轻度帮助、可靠合作、小型阵营利益。
- `+3`：明确支援、承担风险、完成具有阵营意义的协作。
- `+5`：重大救援、关键情报、显著扭转阵营利益。
- `-1`：轻度摩擦、冒犯、违背小型承诺。
- `-5`：明显损害阵营利益、蓄意欺骗或敌对行动。
- `-10`：重大背叛、严重伤害重要成员、破坏关键任务。
- `-50`：极端阵营级背叛或不可逆灾难性敌对行为；必须极少使用。

结算原则：

- 个人私交默认只进入咩咩原生 `<affinity>`，不得自动传播成阵营好感。
- 帮助汽车人不自动等于霸天虎扣分；只有霸天虎确实知情并且利益实际受损时才结算。
- 帮助霸天虎同理。
- 阵营好感变化必须对应正文已经发生或明确确认的事实，不能凭模型“感觉”结算。
- 任何变化后最终值执行 `MAX(-100, MIN(100, 原值 + 本回合变化))`。

## 7. 与咩咩原生人物好感的关系

角色个人关系继续使用咩咩预设原生 `<affinity>`。

MVU 不建立 97 人第二套好感表。

因此：

- 何博玟对玩家的个人好感 = 咩咩原生 affinity。
- 汽车人阵营对玩家的整体态度 = `<causality>` 汽车人好感。
- 薇震天对玩家的个人好感 = 咩咩原生 affinity。
- 霸天虎阵营对玩家的整体态度 = `<causality>` 霸天虎好感。

两套含义不同，允许方向不一致。

例：玩家可能得到某名霸天虎角色的高度私人信任，但霸天虎整体仍然警戒玩家。

## 8. 读取与实时刷新

必须继承《无职转生·因果法典》后续楼层实时刷新修复经验。

消息识别不得写死 `role === 'assistant'`。

推荐兼容判断：

- `is_user !== true`
- `is_system !== true`
- `role` 缺失时仍允许识别模型消息
- 排除 user / system / tool

读取策略：

1. 从最新消息向前扫描。
2. 只读取模型消息。
3. 找到最后一个合法完整 `<causality>` 即停止。
4. 最新楼层块损坏时自动回退上一合法块，UI 不归零。

实时监听至少包括：

- 新 assistant 消息渲染 / 收到
- 消息编辑
- swipe
- 删除消息
- chat change
- MVU variable initialized / update ended（用于与咩咩生命周期兼容，即使本模块不把阵营值写进变量）
- 必要时以 MutationObserver 作最终 DOM 保险

不得每轮复制第二套完整 MVU DOM；始终只有一个全局实例。

## 9. 咩咩全栈技术条目

静静可以制作 MVU 所需四条技术条目，但必须作为独立片段交付，不修改业务世界书：

1. `[mvu_update]变量更新规则`
2. `[mvu_update]变量输出格式`
3. `变量列表`
4. `[initvar]变量初始化勿开`

本卡没有可写阵营好感 stat_data，因此更新规则必须明确：

- 汽车人 / 霸天虎好感禁止写入 stat_data 或 JSONPatch。
- 若运行环境要求 `<UpdateVariable>`，JSONPatch 保持空数组。
- `<causality>` 是阵营好感唯一真值源。

四条技术条目字段严格沿用咩咩全栈空模板成熟口径：

- `use_regex=true`
- `scan_depth=null`
- `prevent_recursion=true`
- `exclude_recursion=true`
- `@Depth 0`

initvar 仍按全栈约定保持禁用。

## 10. MVU 脚本层建议

脚本保持三件套：

1. `MVU`：保留官方 / 咩咩全栈原始 MVU core import。
2. `MVU ZOD`：本卡无业务持久变量，使用空对象 passthrough schema，避免剥掉其他原生变量。
3. `变形钢姬 · 独立MVU`：只加载本项目固定 commit 的独立 runtime。

独立 runtime 建议目录：

`modules/steel-maidens-mvu/`

至少包含：

- `src/`
- `dist/steel-maidens-mvu.js`
- `README.md`
- `qa/`

正式成卡只引用固定 commit CDN，不引用 `main` 浮动地址。

## 11. 手机与交互硬要求

- Android / SillyTavern 优先。
- 320 / 360 / 390 / 412 / 430px 视口均不得横向溢出。
- 关键按钮真实触控区 ≥44×44px。
- 两页允许底部 Tab 点击切换。
- 同时允许左右滑动切页。
- 滑动页面不得误触网易云 iframe 控件。
- 返回锁屏后音乐不断播。
- chat changed / 模块 disable 时正确清理监听器和 iframe。

## 12. 第一页视觉方向

视觉基调：电影机械质感 + 《变形钢姬》女性钢铁文明，不做花哨 RPG 仪表盘。

建议：

- 汽车人卡片：暗红 / 钢灰，标志作为淡水印。
- 霸天虎卡片：暗紫 / 钢灰，标志作为淡水印。
- 两个数值居中突出。
- 进度条以 0 为中心向左右延伸，负值与正值方向直观可见。
- 本回合变化值小号显示，例如 `+3` / `-5`。
- 原因只显示一行，超长省略，点击或展开后可看完整原因。

不得加入第三阵营、角色头像墙、收藏册或复杂地图。

## 14. QA 必测

1. 首轮无旧块：两方均 0。
2. 每轮有完整合法 `<causality>`：UI 正确更新。
3. 最新块损坏：回退上一合法块，不归零。
4. swipe：切换后立即显示当前分支最新合法块。
5. 编辑消息：立即更新。
6. 删除消息：回退上一合法块。
7. role 缺失但 `is_user !== true`：仍能识别模型消息。
8. 两方变化互不自动镜像。
9. 单个角色 `<affinity>` 变化不自动改阵营。
10. 网易云页面切换 / 返回锁屏后持续播放。
11. DOM 重渲染后仍只有一个播放器实例和一个 MVU 实例。
12. 世界书业务文件 SHA 在静静施工前后完全不变。

## 15. 当前冻结结论

《变形钢姬》MVU 采用：

**双阵营半屏锁屏 → 两页 MVU（阵营好感 / 网易云） → `<causality>` 唯一阵营真值 → 咩咩原生 `<affinity>` 继续负责人际关系。**

核心原则：极简、单一真值源、实时回退、手机优先、世界书业务层零修改。
