## 二、人物总名册继承规则

以下五项必须以 `docs/001_变形钢姬_人物总名册_v0.3.md` 为唯一上游事实源：

1. `阵营`
2. `定位`
3. `变形载具`
4. `外貌锚点`
5. `性征武装模块`

### 外貌锚点硬规则

- `外貌锚点` 必须逐字继承人物总名册对应角色的现行内容，不得在人物条目中另起一套“鲜明特征”。
- 例如何博玟固定为：`红蓝骑士式重甲；胸前车窗与双肩排气结构`。
- 例如薇震天固定为：`银黑尖刺重甲；锋利面部与红色光学镜`。
- `头部主色 / 头部结构 / 光学镜 / 胸甲结构 / 上身装甲 / 下身装甲 / 外置结构 / 足部结构` 只能围绕外貌锚点展开细节，不得与锚点冲突或覆盖其辨识度。
- 若逐角精修确实发现锚点必须调整，必须先更新总名册与对应 QA，再同步人物条目；禁止只改下游人物条目。

### 阵营 / 定位 / 载具 / 性征武装硬规则

- 阵营不得把单场临时合作写成永久归属。
- 定位只记录长期稳定职责、组织角色与战术定位，不写一次性战果。
- 变形载具按电影阶段顺序继承总名册；电影镜头、官方玩具、概念/衍生资料的事实等级不得混写。
- 性征武装模块的人物栏只继承总名册中的正式名称、类型与核心用途；完整机制统一进入对应能力条目。

## 三、字段职责

### 名字
只写现行娘化名。正式人物正文不得把原名当显示名。

### 性别
普通赛博坦角色统一写世界内事实：`女性（双重性征）`。不得出现“娘化”“原男性”等元叙事。

### 阵营
逐角继承总名册。

### 定位
逐角继承总名册。

### 变形载具
逐角继承总名册；跨电影换型按时间顺序列出。

### 外貌锚点
逐字继承总名册，用于锁定角色最鲜明、最不可漂移的视觉识别点。

### 印象
1～3 句概括第一性格印象、机体气质、最关键的历史或关系锚点；已有独立字段的阵营、定位、载具不机械重复。

### 头部主色
写头部装甲、机械缆线、冠状结构的主要颜色与点缀色；不得生成“发色”。

### 头部结构
写头冠、面罩、天线、鳍片、机械须、辫须、缆线、翼片等真实结构；不得凭空添加人类发型。

### 光学镜
写颜色、数量、形态、亮度与特殊结构。独眼、多眼、遮罩式结构必须明确。

### 机体比例
必须包含：身高、质量/体重、机体规格、肩腰胯与四肢比例、装甲厚薄和整体女性化机械轮廓。官方缺少精确质量时允许合理推定，但 QA 必须明确标注为 AU 制卡估算。

### 胸甲结构
必须包含字母罩杯的等效视觉体量，并描述胸甲、车窗、前舱、装甲件与活体机械组织的结构关系。罩杯仅作为制卡视觉尺度。

### 上身装甲
写胸甲、肩甲、背甲、车窗、格栅、排气管、机翼、旋翼、炮塔等上半身结构；不得削弱总名册外貌锚点。

### 下身装甲
写骨盆、腰胯、大腿、小腿、侧甲、轮组、履带等下半身结构。

### 外置结构
写徽记、面罩、天线、轮组、挂点、缆线、纪念涂装、外置工具等；不得在这里展开性征武装完整机制。

### 足部结构
写足部装甲、轮组、履带、抓地、起落、滑行或推进结构。

### 性征武装模块
即制卡工程中的“扶她武器模块”。正式 worldbook 统一使用内世界术语 `性征武装模块`。人物栏只写模块名称、武器/工具类型和一句核心用途；供能、冷却、拆离反馈、损伤后果全部进入能力条目。

## 四、心理模型：完全保留咩咩原生四槽

固定为：

```text
心理模型:
- Trauma:
- Defense:
- Trigger:
- Need:
```

- `Trauma`：核心创伤、失败、失去、羞辱、背叛、战争记忆或长期责任。
- `Defense`：角色在压力、亲密、失败或威胁下最稳定的心理防御方式。
- `Trigger`：能稳定触发核心情绪与防御方式、可以实际用于 RP 的具体情境。
- `Need`：深层而稳定的心理需要，不等于“想赢”“想杀敌”“需要 Energon”。

四槽必须形成：`Trauma → Defense → Trigger → Need` 的人格因果链。

## 五、对话范例

- 固定三句中文直接对话；
- 不写旁白或“她说道”；
- 三句分别体现语言节奏、立场与心理模型；
- 不写同义三连；
- 不无依据加入现代人类网络口癖。

## 六、能力条目

能力独立使用：

```text
<核心设定:【角色名】·能力>
……能力正文……
</核心设定:【角色名】·能力>
```

能力正文原则上闭环交代：机体规格与基础能力、替代形态、性征武装完整机制、常规武装、战斗方式、特殊技术或权限、Energon/火种/热负荷/弹药约束、受损与过载后果、明确限制。

## 七、GitHub 源文件可读性规则

GitHub Markdown `Preview` 会把连续的普通单换行折叠为同一段落，因此旧样板在 Preview 中会看起来像“没有换行”；`Code` 视图中的原始文件实际上仍保留换行。

为便于手机端直接在 Preview 审核，后续所有人物 `.md` 源文件统一：

- 每个顶层字段之间保留一个空行；
- `心理模型:` 与四槽之间保持正常列表结构；
- 三句对话之间各保留一个空行；
- 不使用 `<br>`；
- 不使用 Markdown 代码围栏包裹正式 worldbook 正文；
- 不依赖行尾双空格这种易丢失的 Markdown hard-break 技巧。

空行只用于源文件可读性，不构成新的 worldbook 字段，也不改变语义。

## 八、人物与能力职责边界

人物条目回答：她是谁、属于谁、承担什么职责、变成什么、最鲜明的外貌锚点是什么、完整机体长什么样、性征武装是什么、人格为什么这样形成、她如何说话。

能力条目回答：她能做什么、为什么能做到、如何变形与战斗、性征武装如何运行、特殊权限如何工作、代价与损伤后果是什么。

同一机制不得在两条中大段重复。

## 九、生产前检查清单

每名角色进入正式世界书前必须确认：

1. 标签为 `<角色名character>`；
2. `阵营 / 定位 / 变形载具 / 外貌锚点 / 性征武装模块` 五项均从总名册继承；
3. `外貌锚点` 与总名册逐字一致；
4. 九个赛博坦机械外貌字段完整且不得与外貌锚点冲突；
5. 机体比例含身高、质量/体重、体态；
6. 胸甲结构含罩杯字母等效视觉体量；
7. 不凭空生成人类头发、布制服装或独立鞋具；
8. Trauma / Defense / Trigger / Need 完整且成因果链；
9. 三句对话齐全且能区分角色；
10. 能力独立拆入 `<核心设定:角色名·能力>`；
11. 人物栏性征武装只做摘要，完整机制留在能力条目；
12. 能力存在真实负荷、损伤、供能与边界；
13. 人物 `.md` 顶层字段之间有空行，GitHub Preview 可直接审核；
14. 原名不进入正式人物正文与正式剧情输出。
